<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client -> HTTP start endpoint | Untrusted request payload crosses into the control plane. |
| HTTP start endpoint -> Temporal client | Start requests become workflow executions and must preserve idempotency. |
| Workflow -> PostgreSQL run ledger | Duplicate detection and status persistence rely on a durable store. |
| Workflow -> source repository auth check | Source-read credentials are validated before any expensive work begins. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | T | POST /v1/docs/runs | mitigate | Validate packageName, sourceRepo, and gitHash at the handler boundary before calling Temporal; reject malformed JSON and missing fields with 400. |
| T-01-02 | S/T | Workflow start path | mitigate | Use the deterministic workflow ID docs/{packageName}/{gitHash} and a unique ledger constraint so duplicate starts are rejected instead of replayed or auto-restarted. |
| T-01-03 | I | Search attributes | mitigate | Emit only the locked allowlisted fields and exclude secrets, tokens, and raw credentials from search metadata. |
| T-01-04 | D | Run ledger / start endpoint | mitigate | Make duplicate detection and Temporal start conflicts fast-fail with explicit duplicate responses so repeated submissions do not create unbounded retries or duplicate workflow pressure. |
| T-01-05 | E | Auth preflight | accept | Phase 1 only checks source read access and intentionally defers output write checks until the publish phase; no privileged publish path exists yet. |

</threat_model>
